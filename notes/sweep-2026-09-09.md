## Findings

### 1. `visibleClassIDs` turns a fail-closed sentinel into fail-open (new)

`fff5ecc` added `handlers.go:365` `visibleClassIDs`, which returns `nil` for an
admin and treats nil at all three call sites as "show everything". For a parent
it returns `store.ParentClassIDs(db, c)` -- and that function returns `nil` when
its query errors:

    rows, err := db.Query(`SELECT enrolled_classes FROM students ...`)
    if err != nil {
        return nil
    }

Every pre-existing caller passes that map into a filter that does `classIDs[id]`,
and a lookup on a nil map is false, so they all fail closed. `visibleClassIDs`
is the first caller to give nil a second meaning.

Failure: a parent calls `GET /api/session-overrides` during a transient DB error
-- a connection blip, a statement timeout -- and receives every teacher swap,
move and cancellation in the centre, with the free-text note and the admin's
email in `created_by`. That is precisely the disclosure the commit was written to
close, reachable by making the query fail instead of succeed.

FIXED. Both halves, because either alone leaves the coupling that caused it:
`ParentClassIDs` now returns an empty map on error and logs, and
`visibleClassIDs` returns `(map[string]bool, bool)` so "unrestricted" is its own
value. Regression test `TestParentClassScopeFailsClosed`, seen failing on the
old code.

Related, smaller: all three lists apply `LIMIT 5000` before the role filter, so a
non-admin whose records sit past the first 5000 rows silently sees fewer.

### 2. Reversing a Paid invoice does not unwind the referral milestone (new)

`a5bd610` added `"Unpaid"` to the status whitelist -- it was not there before, so
this path is newly reachable, not merely newly exposed.

`handlers_invoices.go:569` re-evaluates the referral only on
`newStatus == "Paid"`, and `ReferralCheckMilestoneOnPay` returns immediately
unless `status == 'pending'`. Nothing anywhere decrements or re-opens an earned
reward.

So an invoice paid in error, counted toward the three-invoice milestone, then
reversed, leaves `status='earned', credits_remaining=3` standing on a paid count
that is now two. The correction that was supposed to undo the payment leaves the
reward it triggered in place.

FIXED. `ReferralCheckMilestoneOnPay` is now `ReferralReconcile` -- one function
that re-derives the reward in both directions, called on Paid and on Unpaid, so
the rule stays defined once instead of growing a near-twin. A reward whose
credits are already partly spent is deliberately NOT clawed back: that benefit
has usually reached a real invoice, and un-granting it silently would turn the
correction of one mistake into a second one. Those are logged as
`referral_milestone_stale` for an admin to settle. Judgement call, flagged.

Tests `TestReferralMilestoneUnwindsWhenAPaymentIsReversed` and
`TestReferralMilestoneKeepsPartlySpentCredits`, both seen failing on the old
code with exactly the reported symptom (earned/3 credits standing on a count
of 2).

Blast radius still unverified: reading `referral_rewards` on the droplet was
blocked.

### 3. A reversal is audit-logged as a payment (new half, old half)

Same handler. `LogAudit(..., "invoice_paid", ...)`, with a detail blob carrying
`"paidOn": <today>`, sits outside any status guard and outside the
`rowsChanged > 0` guard. Setting an invoice to Unpaid writes an audit row saying
it was paid, dated today; a no-op re-pay writes one too. The trail records that
the endpoint ran, not what it did. The reversal half arrived with `a5bd610`; the
no-op half predates it.

FIXED. `invoiceAuditAction` names the row after the transition
(`invoice_paid` / `invoice_payment_reversed` / `invoice_status_changed`),
`paidOn` and `method` appear only on an actual payment, and the whole block is
gated on `rowsChanged > 0`. Tests `TestReversalIsNotAuditedAsAPayment` and
`TestRepayNoOpWritesNoAuditRow`.

### 4. The rate-limit fix never reached production, and its stated reason is wrong

`5524b37` touches only `infra/Caddyfile.recommended` and
`AI_DOCS/auth-and-tenancy.md`. Nothing in the Makefile, scripts/ or CI copies a
Caddyfile to the droplet, so `make ship` cannot deploy it. The live
`/etc/caddy/Caddyfile` proxies with a bare `reverse_proxy localhost:8080` -- no
`header_up`, no `trusted_proxies`.

The commit's reasoning is that Caddy appends to an inbound `X-Forwarded-For`.
Tested against caddy:2.11 with the production directive shape, that is not what
happens:

    inbound X-Forwarded-For: 1.2.3.4   ->  upstream sees XFF=172.17.0.1   (replaced)
    inbound X-Real-IP: 9.9.9.9         ->  upstream sees XRI=9.9.9.9      (passed through)

Caddy replaces XFF and neither sets nor strips `X-Real-IP`. `core.RealIP` checks
`X-Real-IP` first and trusts any header from a loopback peer, which localhost
always is. So the bypass is real but through the other header: a client sending
`X-Real-IP: <anything>` picks its own bucket, and a fresh value per request means
the per-IP login limiter never fires.

FIXED IN CODE, which matters because the Caddyfile cannot be deployed by
`make ship`. `core.RealIP` no longer reads `X-Real-IP` at all and takes the
RIGHT-most `X-Forwarded-For` entry -- the one the nearest proxy wrote, correct
whether that proxy replaces the header or appends to it, and unspoofable in
both cases. `store.refresh_tokens.clientIP`, which stored the raw header
verbatim as the forensic IP with no trust check at all, now goes through the
same helper.

Tests `TestRealIPIgnoresClientSuppliedHeaders` and
`TestRealIPBucketIsStableUnderSpoofing`, seen failing on the old code including
the rotating-header case.

`infra/Caddyfile.recommended` and `AI_DOCS/auth-and-tenancy.md` both stated the
append mechanism as fact; both now carry the measured table instead. The
`header_up` lines stay as defence in depth, but the app no longer depends on
them, so this ships through the normal deploy path.

### 5. WITHDRAWN -- not a bug

I reported that `handlers_cancelled.go:219` lets a superadmin's delete match
nothing and report success. Re-reading the handler before changing it: the
`SELECT ... WHERE tenant_id=?` above it fails first for tenant 0 and returns 404,
so the caller gets an honest failure, not a false success. A superadmin cannot
delete a cancelled class -- consistent with "reads across tenants, does not write
into them" -- and it fails closed. Nothing to fix.

`32196c5`'s own claim does hold: all 43 insert-feeding sites go through
`writeTenant`, and every remaining bare `store.TenantID` call feeds a read.

### 7. `8fe1d67` fails open on a RowsAffected error

`if n, raErr := res.RowsAffected(); raErr == nil && n == 0` treats a driver error
as "rows were affected" and proceeds to count and email. Narrow, but the safe
branch is the other one.

FIXED. An unreadable count now rolls back and skips the student, same as a zero
count: the student is left unbilled and visibly so, rather than emailed about an
invoice the run cannot confirm it created.
